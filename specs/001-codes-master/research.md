# Codes Master Research

**Date**: 2026-10-29  
**Feature**: [spec.md](spec.md)

## Decisions

### 1. Use the existing Oracle table with database-first EF Core

- **Decision**: Use `IIRIS_RD_DEVP.STD_CODES` as the sole source of truth. Follow the constitution's Oracle Entity Framework Core database-first approach, do not edit scaffolded entities, add partial extensions only when needed, and do not use migrations or change the schema.
- **Rationale**: The specification identifies this table as authoritative and prohibits schema changes. The constitution requires Oracle.EntityFrameworkCore and database-first.
- **Alternatives considered**: A replacement table, migrations, or a separately maintained data store were rejected because each conflicts with the approved specification/constitution.
- **Evidence**: [Constitution B8](../../.specify/memory/constitution.md); [Codes Master specification](spec.md), FR-009–FR-014.
- **Implementation prerequisite**: The current API project has no Oracle provider, DbContext, scaffolded entity, or database configuration. Package version/license approval, authorized read-only schema inspection, and confirmation of connectivity are required before implementation. This planning task does not install a provider or connect to the database.

### 2. Keep creation audit generation at the database boundary

- **Decision**: Create records with `CC_CR_BY = 'ADMIN'` and `CC_CR_DT` generated by Oracle `SYSDATE`; preserve both values on update. Keep `CC_UP_BY` and `CC_UP_DT` NULL.
- **Rationale**: These are explicit feature requirements and avoid browser/session-provided audit values. Oracle documents that `SYSDATE` uses the operating-system clock of the database server and returns an Oracle `DATE`.
- **Alternatives considered**: Browser timestamps, application-server timestamps, and update audit values were rejected by the specification.
- **Evidence**: [Oracle 19c SYSDATE](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/SYSDATE.html); [Codes Master specification](spec.md), FR-025–FR-030.
- **Implementation prerequisite**: Verify the database server's configured time zone/clock before implementing the required GST display. The table's `DATE` value has no stored time-zone offset; do not assume the database host is configured to GST.

### 3. Enforce Oracle byte-length semantics with Oracle authoritative

- **Decision**: Retain UI validation for usability and enforce the final byte-length rule on the server using behavior that matches the target Oracle database character set. Oracle remains the final constraint authority; translate length failures to safe field-level feedback and never truncate silently.
- **Rationale**: The columns are explicitly `VARCHAR2(... BYTE)`. Counting Unicode characters alone is insufficient. Oracle documents that `LENGTHB` measures bytes, unlike `LENGTH`, which measures characters.
- **Alternatives considered**: Character-count-only validation was rejected because it cannot prove the Oracle byte limit. Assuming UTF-8 bytes without verifying the database character set was rejected.
- **Evidence**: [Oracle 19c LENGTH and LENGTHB](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/LENGTH.html); [Codes Master specification](spec.md), FR-016–FR-020.
- **Implementation prerequisite**: During authorized read-only database inspection, confirm the database character set and select/verify a pre-persistence check compatible with that target. The column constraints remain the final safeguard.

### 4. Keep record identity composite through every operation

- **Decision**: Use `(CC_CODE, CC_TYPE)` for lookup, update, delete, and duplicate handling. Derive `CC_COMP_CODE` directly from `CC_CODE`.
- **Rationale**: The table's primary key is composite, and a Code may appear with a different Type.
- **Alternatives considered**: Code-only identification or an added uniqueness rule was rejected because it would alter data identity.
- **Evidence**: [Codes Master specification](spec.md), FR-010–FR-013 and FR-031–FR-032.

### 5. Use OpenAPI as the API/client contract

- **Decision**: Define controller request/response shapes in API return types and publish the contract through OpenAPI. Generate the Angular client from that contract; do not hand-write generated API models. Use the required paginated shape and `ProblemDetails` for non-success responses.
- **Rationale**: This follows the constitution and gives API and UI a single agreed contract.
- **Alternatives considered**: A manually duplicated UI API model or a hand-maintained client was rejected by the constitution.
- **Evidence**: [Constitution B6–B8](../../.specify/memory/constitution.md); [API contract](contracts/codes-master.openapi.yaml).
- **Implementation prerequisite**: No OpenAPI client-generation setup, global HTTP error interceptor, shared pagination type, or Oracle-backed API exists yet. Select/approve any package changes before adding them.

### 6. Keep the existing application layout and record execution gaps

- **Decision**: Extend the existing .NET API and Angular UI. Keep database operations in an API service and feature routes/pages in the UI. Do not add runtime projects or dependencies as part of planning.
- **Rationale**: The repository already has the two application projects, and the constitution favors the simplest design that meets the feature.
- **Alternatives considered**: A new application or a parallel data store was rejected as unnecessary and out of scope.
- **Evidence**: API project files under `Spec-Driven-Development/SDD.API/SDD.API/`; UI project under `Spec-Driven-Development/sdd-ui/`.
- **Implementation prerequisite**: The constitution specifies Angular 21, Angular Material, xUnit, and Playwright. The repository currently declares Angular 22.2 and does not include Angular Material, an API test project, or Playwright setup. Reconcile package/version choices and obtain owner approval before changing dependencies. No constitution amendment is proposed by this plan.

### 7. Apply column filters in the database before pagination

- **Decision**: Add optional operator/value query parameters for the five displayed data columns. Validate operators against an allowlist, apply case-insensitive predicates to the matching Oracle columns, combine active filters using AND, then count and page the filtered query. Escape LIKE wildcards so filter values are treated literally.
- **Rationale**: The user requires filters to find matches across all records, not only the current page. Filtering in the database preserves accurate pagination and avoids fetching the full table into the UI.
- **Alternatives considered**: Filtering only the already-loaded page was rejected because it can hide matches on other pages. Fetching every row and filtering in memory was rejected because it scales with the entire table and bypasses database pagination.
- **Evidence**: Clarifications in [spec.md](spec.md), FR-035–FR-036; Oracle-backed `STD_CODES` list operations in the existing API.
- **Contract**: The optional per-column query parameter pairs are defined in [contracts/codes-master.openapi.yaml](contracts/codes-master.openapi.yaml). The Angular client remains generated from that contract.

## Alternatives Summary

| Concern | Chosen direction | Rejected alternative |
|---|---|---|
| Persistence | Existing Oracle `STD_CODES`, database-first | New table, schema migration, replacement store |
| Record identity | Composite Code + Type | Code-only key |
| Audit fields | Oracle `SYSDATE`, `ADMIN`, preserve creation values | Browser/session values or update audit tracking |
| Validation | UI assistance plus Oracle-compatible server validation | Character count alone or silent truncation |
| Listing filters | Allowlisted, case-insensitive Oracle predicates before pagination; active filters combine with AND | Current-page-only or full-table client filtering |
| API/client contract | OpenAPI source of truth, generated Angular client | Hand-maintained duplicate client models |
| Application layout | Extend existing API and UI | New runtime project or unrelated architecture |
